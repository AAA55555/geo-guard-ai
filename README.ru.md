# geo-guard-ai

[![npm version](https://img.shields.io/npm/v/geo-guard-ai.svg)](https://www.npmjs.com/package/geo-guard-ai)

[English](./README.md) · **Русский**

**Гео-ограничение для AI CLI.** Разрешает запуск Claude Code (или другой команды) только если твой внешний IP резолвится в разрешённую страну. Если ты не там, где нужно, — блокирует ещё до отправки промпта.

Так же гейтит чат **Cursor** (IDE и `cursor-agent`) — через собственный конфиг hooks, см. [Cursor](#cursor) ниже.

Кроссплатформенно: **macOS / Linux / Windows**. TypeScript, рантайм — Node **18.20+ или 20.12+** (не 18.0–18.19, не 19.x, не 20.0–20.11: именно в этих версиях `spawn` отказывается запускать `.cmd` на Windows).

Язык CLI — **английский или русский**, определяется автоматически по локали машины (`LC_ALL` / `LC_MESSAGES` / `LANG`), по умолчанию английский. Принудительно: `GEO_GUARD_LANG=en|ru`.

---

## Зачем это нужно

Иногда работать с AI-инструментом можно только из определённой страны — из-за политики компании, условий заказчика, юрисдикции или личного правила «не работаю не оттуда». Проблема в том, что легко забыть: VPN отвалился, уехал, сеть переключилась — а ты продолжаешь работать как ни в чём не бывало.

`geo-guard-ai` — это **страховка от «случайно продолжил не оттуда»**. Он проверяет страну по внешнему IP в двух точках:

| Точка контроля | Что делает |
|---|---|
| **Запуск команды** | набранный `claude` попадает в маленький **shim** в твоём `PATH`: тот сначала проверяет страну и только потом запускает настоящий Claude Code. То же самое для `cursor-agent` |
| **Каждый промпт** | Claude Code hook `UserPromptSubmit` вызывает `geo-guard check` перед отправкой каждого промпта; страна не разрешена → промпт блокируется (exit 2) |

Вторая точка важна: сессию можно запустить в разрешённой стране, а через час VPN отвалится — hook поймает это на следующем промпте.

### Покрытие

| Где | Гейтится через |
|---|---|
| Терминал / встроенный терминал IDE | shim `claude` в `PATH` → обёртку `geo-guard claude` |
| Панель расширения Claude Code | hook `UserPromptSubmit` в `~/.claude/settings.json` |
| Чат Cursor (IDE) | hook `beforeSubmitPrompt` в `~/.cursor/hooks.json` |
| `cursor-agent` (терминал) | shim `cursor-agent` в `PATH` → обёртку `geo-guard cursor-agent`, плюс тот же hook в `~/.cursor/hooks.json` |

**Поведение fail-closed:** нет сети или ни один провайдер не ответил → блок. Лучше перебдеть.

## Как работает

1. Внешний IP → страна (ISO-код) через публичные провайдеры (`ifconfig.co`, `ipinfo.io` по умолчанию). Провайдеры опрашиваются **параллельно** — побеждает первый валидный ответ (`Promise.any`).
2. Страна сверяется со списком `allowed`.

Проверка всегда **свежая** — без кэша. Каждый вызов `check` (то есть каждый промпт) заново определяет страну, поэтому отвал VPN ловится на следующем же промпте, а не через какое-то окно.

## Чем это НЕ является

Это **не механизм безопасности**, а бытовая страховка. Обходится тривиально:

- запуском настоящего бинаря по полному пути или постановкой его в `PATH` перед shim,
- удалением hook (Claude Code или Cursor),
- любым VPN в разрешённой стране.

Смысл — не «защитить», а не дать *случайно* продолжить работу не оттуда.

## Установка

```bash
npm install -g geo-guard-ai
geo-guard setup
```

`setup` в интерактиве спросит:

1. **разрешённые страны** (ISO через запятую, дефолт `NL`);
2. ставить ли **Claude Code hook** (дефолт да);
3. ставить ли **hook Cursor** — спрашивается, только если есть `~/.cursor` (дефолт да);
4. нужен ли **Cursor отдельный список стран** — спрашивается, только если ставим hook Cursor (дефолт нет; см. [Разные страны для разных инструментов](#разные-страны-для-разных-инструментов));
5. ставить ли **гейт на запуск `claude`** — shim в твоём `PATH` (дефолт да);
6. ставить ли такой же **гейт на `cursor-agent`** — спрашивается, только если `cursor-agent` есть в `PATH` (дефолт да);
7. **с какими флагами гейт должен запускать команду** — спрашивается, только если есть что сохранять (из shim или из заменяемого alias-блока), и они же предлагаются по умолчанию;
8. в чьи **rc** прописать `PATH` — определённый shell предлагается по умолчанию; ответь `all`, чтобы во все, что у тебя есть.

Дефолт для стран — то, что настроено сейчас, так что повторный проход с Enter'ами ничего не меняет.

Без вопросов (CI / скрипты):

```bash
geo-guard setup --countries ES,PT --yes
```

С `--yes` hook Cursor ставится автоматически **только если `~/.cursor` уже существует**; передай `--cursor`, чтобы поставить его в любом случае (например, готовишь машину заранее, до установки самого Cursor), или `--no-cursor`, чтобы пропустить:

```bash
geo-guard setup --yes --cursor      # принудительно, даже без ~/.cursor
geo-guard setup --yes --no-cursor   # пропустить
```

Повторный `setup` **не сбрасывает** кастомные `timeoutMs` / `providers` в конфиге — обновляет только `allowed`.

### Как сменить страну

```bash
geo-guard config --countries NL
```

Трогает **только** `config.json` — rc и оба hook-конфига не задеваются. `geo-guard setup -y -c NL` тоже сработает, но он заново проходит всю установку; для рутинной смены лучше `config`.

`setup` больше ничего не сбрасывает без спроса: запуск без `--countries` оставляет настроенный список как есть (и `timeoutMs`, и `providers`, и профили тоже).

Разовая проверка без записи в конфиг: `GEO_GUARD_ALLOWED=NL geo-guard check`.

### Как вернуть дефолты

```bash
geo-guard config --reset                  # весь конфиг, вместе с профилями
geo-guard config --reset --profile cursor # только один профиль (то же, что --unset)
```

`--reset` оставляет `config.json` ровно таким, каким его делает свежая установка: `allowed: ["NL"]`, дефолтные `timeoutMs` и `providers`, без `profiles`. Ничего не переустанавливает и не удаляет — hook-конфиги, shim и rc не трогаются, так что, в отличие от `uninstall`, защита продолжает работать, просто по дефолтной политике.

`setup` проверяет всё, что может отказать, **до** первой записи: если `~/.claude/settings.json` или `~/.cursor/hooks.json` — невалидный JSON либо секция хуков не той формы, которую пишут эти инструменты (например, в `"UserPromptSubmit"` лежит строка), ты получишь сообщение с именем файла и ключа, и ничего не изменится вообще. geo-guard не переписывает данные, которых не понимает, и не оставляет тебя с конфигом, но без хука. Непонятные записи *внутри* корректного списка просто обходятся и остаются на месте.

## Гейт на запуск

Пойнт установки — сделать так, чтобы привычная команда `claude` шла через проверку. geo-guard делает это через **shim**: крошечный исполняемый файл с именем команды, в нашем каталоге, который встаёт в `PATH` первым.

```
~/.geo-guard/bin/claude        # на Windows: ~/.geo-guard/bin/claude.cmd
```

```sh
#!/bin/sh
# >>> geo-guard-ai shim v1: claude >>>
# Managed by geo-guard-ai. Do not edit: `geo-guard setup` regenerates this file.
GG="/usr/local/bin/geo-guard"
[ -x "$GG" ] || GG=geo-guard
exec "$GG" claude "$@"
```

…и помеченный маркерами блок в rc, который ставит этот каталог вперёд:

```sh
# >>> geo-guard-ai path begin >>>
case ":$PATH:" in
  *":/Users/me/.geo-guard/bin:"*) ;;
  *) PATH="/Users/me/.geo-guard/bin:$PATH" ;;
esac
export PATH
# <<< geo-guard-ai path end <<<
```

Путь до `geo-guard` зашивается в момент установки — чтобы shim работал из cron-задачи или Makefile, где `PATH` может быть совсем не твоим; если этот путь когда-нибудь исчезнет, shim откатывается на голое `geo-guard`. Строка с `PATH` написана так, что повторный `source` твоего rc не наращивает `PATH` копиями.

### Почему не alias

Раньше вместо этого писался `alias claude="geo-guard claude"`. Alias — удобство интерактивного shell, и он пропускал мимо себя всё, что не является интерактивным вводом в том единственном shell, чей rc мы правили:

| Что набрано | Alias | Shim |
|---|---|---|
| `claude` в том shell, чей rc правил setup | гейтится | гейтится |
| `claude` в shell, чей rc мы не трогали (набрал `bash`) | **проходит** | гейтится |
| `\claude`, `command claude` | **проходит** | гейтится |
| `claude` из скрипта, Makefile, cron, задачи редактора | **проходит** | гейтится |
| `/usr/local/bin/claude` (полный путь) | **проходит** | **проходит** |

Запись в `PATH` читает каждый стартующий shell, а shim — настоящий файл на диске, так что через него проходит всё, что ищет команду по имени. Последняя строка — единственное, с чем не справляется ни то, ни другое, и это одна из причин, почему это страховка, а не безопасность.

`setup` убирает наш старый alias-блок, если его находит, и переносит дописанные тобой флаги в shim: из `alias claude="geo-guard claude --dangerously-skip-permissions"` получается shim, который запускает `geo-guard claude --dangerously-skip-permissions "$@"`. Твои собственные alias не трогаются, и чужое содержимое между нашими маркерами — тоже.

### Флаги, с которыми гейт запускает команду

Гейт может носить твои флаги и подставлять их при каждом запуске — обычно это `--dangerously-skip-permissions`:

```sh
exec "$GG" claude --dangerously-skip-permissions "$@"
```

Задать явно, отдельно на каждую команду:

```bash
geo-guard setup --claude-args "--dangerously-skip-permissions"
geo-guard setup --cursor-args "--force"
geo-guard setup --claude-args ""      # снять
```

Один раз заданные, **они переживают всё**: повторный `setup` ради смены стран, обновление пакета, переустановку. Откуда берутся флаги, в порядке приоритета:

1. `--claude-args` / `--cursor-args`, если переданы (пустое значение — снять);
2. то, что уже лежит в shim, — именно это и делает их постоянными;
3. то, что было в нашем старом блоке `alias claude="geo-guard claude --dangerously-skip-permissions"`, — на тот единственный запуск, который его заменяет;
4. ничего.

Интерактивный `setup` спрашивает про них, **только если есть что сохранять**, и предлагает текущие флаги значением по умолчанию — так что Enter ничего не меняет, а на свежей установке вопроса вообще нет.

Править shim руками тоже можно — прочитается так же. Если изменить тело за пределами строки `exec`, которую мы генерируем, setup перестаёт понимать, что там запускается, и не трогает файл целиком; пересобрать его можно через `--force-shim`.

**Файл с таким именем, который писали не мы, не перезаписывается никогда** — ни с `--force-shim`, ни без: бэкапа нет, а твой собственный бинарь по имени `claude` — ровно то, что гейт на запуск не имеет права съесть. setup сообщает о нём и оставляет как есть.

Твои `timeout` / `statusMessage` / `failClosed` в записях hook (`~/.claude/settings.json`, `~/.cursor/hooks.json`) переживают повторный запуск точно так же — переписывается только `command`.

### Гейт на `cursor-agent`

У терминального клиента Cursor свой shim — `~/.geo-guard/bin/cursor-agent` — и он везде отдельный: свой файл, своя политика по странам (профиль `cursor`), свои флаги, своя строка в `status`, своё удаление. Снос одного гейта никогда не задевает второй.

Ставится, только если `cursor-agent` действительно есть в `PATH`: вешать гейт на команду, которой у тебя нет, — значит заменить честное «command not found» от shell на нашу собственную ошибку. Управляется флагами `--cursor-shim` / `--no-cursor-shim`; `--no-shim` означает «не лезь в мой `PATH`» и покрывает оба.

Зачем это, если `~/.cursor/hooks.json` и так гейтит Cursor? Потому что hook срабатывает только на отправке промпта, а `cursor-agent` рисует заблокированную отправку строкой статуса, которую стирает следующая перерисовка, — причину видно пару секунд, и она исчезает. Блокировка на запуске говорит это один раз, сразу, и остаётся на экране.

### Shells

Каталог с shim нужно добавить в `PATH` в каждом shell, которым ты пользуешься. По умолчанию `setup` пишет в определённый shell; `--shells` принимает список через запятую или `all` — все shell, установленные на машине.

| Shell | Файл, куда идёт запись в `PATH` |
|---|---|
| zsh | `~/.zshrc` |
| bash | `~/.bashrc` |
| fish | `~/.config/fish/config.fish` (через `fish_add_path -p`) |
| PowerShell | `$PROFILE` (`Documents/PowerShell/…` или `~/.config/powershell/…`) |

```bash
geo-guard setup --shells zsh,bash
geo-guard setup --shells all
```

**bash получает запись дважды, и так и надо.** bash читает разные файлы в зависимости от того, как он запущен, и ни один не покрывает другой: *login*-bash (такой запускают Terminal и iTerm на macOS, и такой же получается у `bash -l`, cron и `ssh host 'cmd'`) читает login-файл и никогда `~/.bashrc`, а *интерактивный не-login* bash (такой запускает терминал на Linux) читает `~/.bashrc` и никогда login-файл. Поэтому блок идёт в оба.

Login-файл — тот, который читает сам bash: первый существующий из `~/.bash_profile`, `~/.bash_login`, `~/.profile`, — и `~/.bash_profile` создаётся, только если нет ни одного. Этот порядок важен на Linux, где обычно есть `~/.profile`, а `~/.bash_profile` нет: создав его, мы заслонили бы всё, что положил в `~/.profile` дистрибутив.

Подключить `~/.bashrc` из login-файла — привычный обходной приём на macOS — выглядит так, будто это связывает одно с другим, но нет. Штатный `~/.bashrc` в Debian на второй строке делает `return`, если шелл не интерактивный, так что `bash -lc claude` проскакивает мимо всего, что в него дописано. (Найдено прогоном набора в контейнере Debian, см. `npm run test:docker`.) Плюс это затащило бы весь твой интерактивный конфиг в каждый login-shell — изменение твоего окружения, которого запись в `PATH` не стоит.

**Windows:** профиль PowerShell читают только сессии PowerShell — cmd.exe, ярлык, Проводник и IDE берут `PATH` из пользовательского окружения. Поэтому setup дополнительно добавляет каталог shim'ов в пользовательский `PATH` (`HKCU\Environment`) — он действует на все процессы, запущенные после этого. Трогается только пользовательский scope, значение читается и пишется нераскрытым, а `REG_EXPAND_SZ` остаётся `REG_EXPAND_SZ` — твоя запись вида `%USERPROFILE%\…` продолжит раскрываться. Если сделать это не удалось (нет PowerShell в `PATH`, `PATH` неожиданного типа в реестре), setup честно скажет об этом и назовёт каталог, который надо дописать руками; запись в профиле при этом на месте, так что в PowerShell гейт работает в любом случае.

Задать shell иначе: `GEO_GUARD_SHELL=bash` или `GEO_GUARD_RC=/path/to/rc` — чтобы прибить все операции к одному файлу.

После setup **открой новый терминал** — именно он перечитывает rc и даёт shell новый `PATH`. Пересоурсить тоже можно:

```bash
source ~/.zshrc   # или свой файл
```

Проверить, что всё подхватилось:

```bash
geo-guard status   # exit 0 = гейт на месте и действует
which claude       # должно печатать ~/.geo-guard/bin/claude
```

`status` не просто смотрит на файлы: он проверяет, что каталог с shim есть в `PATH` того shell, в котором ты находишься, и что он стоит **перед** настоящим бинарём. Это и ловит случай «setup отработал, но этот терминал открыт раньше».

## Cursor

Cursor (чат IDE и `cursor-agent`) сам читает конфиги hooks от Claude Code — `~/.claude/settings.json` и проектные аналоги — и импортирует найденные там хуки. Это односторонний импорт при загрузке, а не синхронизация; управляется собственной настройкой Cursor **Third-Party Imports** (по умолчанию включена).

`geo-guard setup` (если есть `~/.cursor`, или с флагом `--cursor`) также пишет hook `beforeSubmitPrompt` прямо в `~/.cursor/hooks.json`, с `failClosed: true`:

```json
{
  "version": 1,
  "hooks": {
    "beforeSubmitPrompt": [
      { "command": "geo-guard check", "timeout": 10, "failClosed": true }
    ]
  }
}
```

Cursor дедуплицирует хуки, импортированные из Claude Code, против хуков, уже объявленных в его собственном конфиге, сравнивая точную строку команды. Поскольку `geo-guard setup` пишет одинаковую команду `geo-guard check` в оба файла, проверка всё равно уходит **один раз за промпт**, а не дважды — явная запись побеждает, а импортированная копия отбрасывается. Убедиться в этом можно в логе хуков Cursor (панель Output → канал hooks): ищи строку `Removed duplicate claude-user hook for beforeSubmitPrompt: command:geo-guard check`.

**`failClosed: true`** означает, что любой сбой hook блокирует промпт — сетевая ошибка, таймаут (10с), крах, **или отсутствие бинаря `geo-guard` в PATH** (exit 127). Последний случай стоит знать отдельно: если пакет снесли не через `geo-guard uninstall` / `npm uninstall -g geo-guard-ai` (например, `--ignore-scripts`, ручное удаление каталога установки, смена версии Node, из-за которой пропал глобальный bin), чат Cursor перестаёт работать полностью — блокируется каждый промпт — пока запись не будет убрана вручную.

**Как выйти из этого состояния:** открой `~/.cursor/hooks.json` (и, для симметрии, `~/.claude/settings.json`) в текстовом редакторе и удали запись hook с `geo-guard check` руками. `geo-guard uninstall` делает то же самое программно, но он не запустится, если причина этого состояния как раз в том, что бинарь пропал.

**Если Third-Party Imports выключен**, импорт из `~/.claude/settings.json` вообще не происходит — тогда явная запись в `~/.cursor/hooks.json` от `geo-guard setup` остаётся *единственным*, что гейтит Cursor, и продолжает работать штатно.

Чтобы увидеть ровно то, что видит хост hook, направь stdout в пайп: `geo-guard check | cat`. На успехе печатает ровно `{"continue":true}` без завершающего перевода строки (это общий контракт `geo-guard check` на любом неинтерактивном stdout, а не особенность Cursor — Claude Code видит те же байты). В интерактивном терминале stdout остаётся пустым, а подтверждение (`✅ Geo-check: RU`) идёт в stderr.

Управляется только **глобальный** `~/.cursor/hooks.json`; проектный `.cursor/hooks.json` вне объёма.

Проверено на: Cursor 3.15.6, `cursor-agent 2026.08.25-3e8eec8`, Claude Code 2.1.227.

## Команды

```bash
geo-guard setup [options]       # настройка
geo-guard uninstall [options]   # убрать hook + гейт на запуск + конфиг
geo-guard config [options]      # показать / изменить разрешённые страны
geo-guard check                 # проверка для hook (exit 0 = ок, 2 = блок)
geo-guard status                # что установлено (exit 0 = всё на месте, 1 = нет)
geo-guard claude [args…]        # обёртка: проверить гео и запустить claude
geo-guard <command> [args…]     # то же для любой команды
geo-guard -- <command> [args…]  # то же, если имя похоже на подкоманду
geo-guard version               # также --version, -v
geo-guard --help                # также help, -h
```

`setup`-опции:

| Опция | Значение |
|---|---|
| `-y, --yes` | без вопросов, дефолты |
| `-c, --countries ES,PT` | разрешённые страны |
| `--shells zsh,bash` \| `all` | в чьи rc прописать `PATH` (дефолт — тот shell, в котором ты сидишь; `all` — все установленные здесь) |
| `--shell zsh` | один shell — то же, что `--shells zsh` |
| `--claude-args "--флаг …"` | флаги, с которыми гейт запускает `claude`; пустое значение — снять. Дальше они держатся сами — см. [Флаги, с которыми гейт запускает команду](#флаги-с-которыми-гейт-запускает-команду) |
| `--cursor-args "--флаг …"` | то же для `cursor-agent` |
| `--force-shim` | пересобрать **наш** shim, тело которого правили за пределами понятной нам строки (по умолчанию — не трогается). Файл, который писали не мы, он не перезаписывает никогда: бэкапа нет, а geo-guard не подменяет то, чего не создавал |
| `--hook` / `--no-hook` | ставить/не ставить hook Claude Code |
| `--cursor` / `--no-cursor` | ставить/не ставить hook Cursor (дефолт: ставить, если есть `~/.cursor`) |
| `--shim` / `--no-shim` | ставить/не ставить гейт на запуск (`--no-shim` покрывает обе команды) |
| `--cursor-shim` / `--no-cursor-shim` | ставить/не ставить гейт на `cursor-agent` (по умолчанию: включён, если `cursor-agent` есть в `PATH`) |
| `--claude-countries ES,PT` | страны только для Claude Code (см. [Разные страны для разных инструментов](#разные-страны-для-разных-инструментов)) |
| `--cursor-countries PL` | страны только для Cursor |

Опции `config` — меняют политику, **не трогая** ни rc, ни оба hook-конфига:

| Опция | Значение |
|---|---|
| *(без опций)* | показать эффективный конфиг |
| `-c, --countries ES,PT` | задать разрешённые страны |
| `-p, --profile claude\|cursor` | применить только к этому инструменту |
| `--unset --profile cursor` | убрать профиль; инструмент вернётся к общему списку |
| `--reset` | вернуть всё к дефолтам, все профили удалить |
| `--reset --profile cursor` | то же, что `--unset --profile cursor` |

## Конфиг

JSON:

- macOS/Linux: `~/.config/geo-guard-ai/config.json`
- Windows: `%APPDATA%\geo-guard-ai\config.json`

```json
{
  "allowed": ["NL"],
  "timeoutMs": 5000,
  "providers": [
    "https://ifconfig.co/country-iso",
    "https://ipinfo.io/country"
  ]
}
```

Env перекрывает файл:

| Переменная | Назначение |
|---|---|
| `GEO_GUARD_ALLOWED` | `ES,PT` |
| `GEO_GUARD_TIMEOUT` | таймаут запроса к провайдеру, **секунды** (в файле `timeoutMs` — миллисекунды) |
| `GEO_GUARD_PROVIDERS` | URL провайдеров через пробел (пусто → провайдеров нет → блок) |
| `GEO_GUARD_ALLOWED_CLAUDE` / `GEO_GUARD_ALLOWED_CURSOR` | то же самое, но только для одного инструмента (аналогично `GEO_GUARD_TIMEOUT_*` / `GEO_GUARD_PROVIDERS_*`) — см. [Разные страны для разных инструментов](#разные-страны-для-разных-инструментов) |
| `GEO_GUARD_PROFILE` | задать профиль для `geo-guard check` принудительно (`claude`, `cursor`) |
| `GEO_GUARD_REAL_BIN` | явный путь к целевому бинарю (в обход поиска в PATH) |
| `GEO_GUARD_CONFIG_DIR` | каталог конфига |
| `XDG_CONFIG_HOME` | не наша, но учитывается: при заданной переменной конфиг живёт в `$XDG_CONFIG_HOME/geo-guard-ai` (macOS/Linux) |
| `GEO_GUARD_CONFIG_FILE` | путь к `config.json` |
| `GEO_GUARD_SHELL` / `GEO_GUARD_RC` | shell / rc-файл для записи в `PATH`. Если `GEO_GUARD_RC` задан, любая команда работает **только** с этим файлом и не трогает системные rc |
| `GEO_GUARD_SHIM_DIR` | где лежат shim'ы гейта (дефолт `~/.geo-guard/bin`) |
| `GEO_GUARD_LANG` | принудительный язык CLI (`en`, `ru`) в обход автоопределения локали машины |

Пустое значение значит разное, и это намеренно: `GEO_GUARD_ALLOWED=''` означает «не разрешено ничего» и блокирует — список стран, который ты осознанно опустошил, не должен молча откатываться к дефолту; у пустого `GEO_GUARD_TIMEOUT` такого смысла нет, и он откатывается.

Провайдер должен отдавать двухбуквенный ISO-код страны текстом (`ES`). Ответ не в формате `^[A-Za-z]{2}$` игнорируется. В `allowed` тоже принимаются **только** ISO alpha-2 (`ES`, `PT`); значения вроде `SPAIN` / `ESP` отклоняются при `setup` и отбрасываются при загрузке конфига. Пустой список `providers` (`[]`) означает «провайдеров нет» → страна не определяется → блок.

### Разные страны для разных инструментов

По умолчанию Claude Code и Cursor живут по одной политике. Если им нужно разойтись — добавляется **профиль**: необязательная секция `profiles`, которая переопределяет общий уровень для одного инструмента:

```json
{
  "allowed": ["NL", "DE"],
  "timeoutMs": 5000,
  "profiles": {
    "cursor": { "allowed": ["PL"] }
  }
}
```

Тут Claude Code разрешён из NL/DE, а Cursor — из PL. Профиль может переопределять `allowed`, `timeoutMs` и `providers`; что не указано — наследуется с общего уровня. Конфиг без `profiles` работает ровно как раньше.

Задаётся из CLI, ни rc, ни hook-конфиги при этом не трогаются:

```bash
geo-guard config                                   # показать эффективную политику по инструментам
geo-guard config --countries NL,DE                 # общий список
geo-guard config --countries PL --profile cursor   # только Cursor
geo-guard config --unset --profile cursor          # вернуть к общему списку
```

```
Конфиг: ~/.config/geo-guard-ai/config.json
  общее    allowed: NL, DE (из файла)   timeout: 5s
  claude   allowed: NL, DE   (наследует)
  cursor   allowed: PL   (свой профиль)
```

Метка показывает, откуда список взялся на самом деле, чтобы переменная окружения в шелле не читалась как настройка из файла: при заданном `GEO_GUARD_ALLOWED_CURSOR=CN` строка cursor скажет `(перебито GEO_GUARD_ALLOWED_CURSOR)`. На содержимое файла env не влияет никогда.

`setup` тоже умеет — сразу при установке: `geo-guard setup --countries NL,DE --cursor-countries PL`, либо ответом на вопрос *«Для Cursor нужен отдельный список стран?»* в интерактиве.

Приоритет, от высшего:

1. `GEO_GUARD_ALLOWED_CLAUDE` / `GEO_GUARD_ALLOWED_CURSOR` (и аналоги `_TIMEOUT_` / `_PROVIDERS_`)
2. `GEO_GUARD_ALLOWED` и соседи
3. `profiles.<инструмент>` в `config.json`
4. верхний уровень `config.json`
5. встроенные дефолты

**Под каким профилем идёт запуск.** `geo-guard <команда>` берёт его из имени команды: `claude` — профиль `claude`, `cursor` и `cursor-agent` — профиль `cursor`. Всё остальное — `geo-guard echo hi` — идёт под общей политикой, потому что ни к какому инструменту не относится. То есть при настроенном `cursor: ["PL"]` `cursor-agent` блокируется на запуске по списку Cursor, а `claude` в том же shell и в ту же секунду стартует по своему.

**Как hook понимает, кто его позвал.** Флагом в команде это сделать нельзя: Cursor импортирует хуки Claude Code и выбрасывает те, чья строка команды побайтово совпадает с его собственной, — именно это совпадение и оставляет одну проверку на промпт вместо двух (см. [Cursor](#cursor)). Поэтому в обоих файлах остаётся одинаковый `geo-guard check`, а профиль определяется в рантайме по JSON, который хост пишет хуку в stdin: Claude Code присылает `hook_event_name: "UserPromptSubmit"`, Cursor — `"beforeSubmitPrompt"`. Это фактический хост, из какого бы файла ни пришла запись.

Если в stdin вообще ничего не пришло — значит `geo-guard check` запустили руками в терминале — применяется **общая** политика, поведение ровно как до появления профилей. Если хост что-то прислал, но опознать его не удалось (мусор или незнакомое имя события), применяется **самая строгая** политика: только те страны, которые разрешены и общим списком, и каждым настроенным профилем. Угадывать, какому инструменту какая политика, — ровно тот случай, где стоит падать в закрытую сторону.

Стоит понимать, чем это оборачивается при непересекающихся списках: `claude: ["NL"]` и `cursor: ["PL"]` в пересечении дают пустоту, то есть неопознанный хост заблокирует каждый промпт. Падать мы хотим именно в эту сторону, но если будущая версия любого из инструментов переименует своё событие, ты увидишь тотальную блокировку, а не предупреждение. `geo-guard check --profile claude` сразу покажет, в этом ли дело.

Профиль можно задать явно, для отладки:

```bash
geo-guard check --profile cursor     # или GEO_GUARD_PROFILE=cursor
```

Когда профилей нигде не настроено, stdin не читается вообще — обычная конфигурация за это не платит.

## Удаление

```bash
geo-guard uninstall               # hook + гейт на запуск + записи в PATH + конфиг
geo-guard uninstall --keep-config # то же, но config.json оставить
geo-guard uninstall -q            # тихо (без вывода), напр. для скриптов
npm uninstall -g geo-guard-ai     # удалить сам пакет
```

> ⚠️ Сначала запусти `geo-guard uninstall`, потом `npm uninstall`. В npm 7+ скрипт `preuninstall` **не выполняется**, поэтому `npm uninstall` сам по себе не снимет хуки и гейт на запуск — они останутся висеть в `~/.claude/settings.json`, `~/.cursor/hooks.json`, `~/.geo-guard/bin` и в rc. Оставшийся shim без `geo-guard`, который он зовёт, ломает запуск `claude`.

`geo-guard uninstall` убирает **только то, что добавлял пакет**:

- наш hook в `~/.claude/settings.json`;
- наш hook в `~/.cursor/hooks.json`;
- оба shim в `~/.geo-guard/bin`, и сам каталог, если в нём больше ничего не осталось;
- маркер-блок с записью в `PATH` (`# >>> geo-guard-ai path begin >>>` …) во всех известных rc, включая тот login-файл bash, куда он попал (`~/.bash_profile`, `~/.bash_login` или `~/.profile`);
- на Windows — каталог shim'ов из пользовательского `PATH`; только эту запись, все остальные остаются как были;
- оба маркер-блока alias от прошлых версий (`# >>> geo-guard-ai begin >>>` … и `# >>> geo-guard-ai cursor-agent begin >>>` …), причём каждый оценивается сам по себе — правка руками в одном не повод оставлять второй;
- `config.json` и пустой каталог конфига.

Если сам бинарь `geo-guard` пропал (см. [Cursor](#cursor) → `failClosed`), `geo-guard uninstall` не запустится — убери записи hook из обоих файлов вручную.

Безопасность при удалении:

- **твои собственные alias и строки с `PATH`** не трогаются, как и файл в `~/.geo-guard/bin`, который писали не мы, — он остаётся, и каталог вместе с ним;
- по умолчанию обходятся все известные rc (`~/.zshrc`, `~/.bashrc`, …). Если задан `GEO_GUARD_RC` — только он: системные rc в этом случае не читаются и не пишутся;
- маркер-блок снимается, даже если ты дописал внутрь свои флаги (`geo-guard claude --dangerously-skip-permissions` — всё ещё наш alias, а shim с твоими флагами — всё ещё наш shim). Но если внутри маркеров лежит **чужое** — вообще не строка `geo-guard` — блок **остаётся как есть**: uninstall его не сносит, а предупреждает. Мало ли что важное туда добавили;
- маркер-блок, у которого снесли строку `# <<< geo-guard-ai end <<<`, **остаётся нетронутым, даже если alias внутри наш** — без этого маркера непонятно, где блок заканчивается, поэтому uninstall предупреждает, а не гадает, где резать;
- наши записи hook и в `settings.json`, и в `hooks.json` убираются **по совпадению строки команды**, одинаково в обоих файлах — даже если ты руками поправил `timeout` или дописал флаг, запись всё равно распознается и уберётся; автоматический `.bak` — твоя страховка, если это не то, чего ты хотел;
- остальной `settings.json` / `hooks.json` и оба `.bak`-файла не трогаются.

## Статус

`geo-guard status` отвечает на вопрос «а оно вообще установлено и работает?» — и **только читает**: ни один файл не создаётся, не меняется и не бэкапится, так что команду безопасно запускать на сломанной установке.

```console
$ geo-guard status
Конфиг: /Users/me/.config/geo-guard-ai/config.json
  общее    allowed: RU, NL (из файла)   timeout: 5s
  claude   allowed: RU, NL   (наследует)
  cursor   allowed: RU, NL   (наследует)
  ✅ файл конфига найден

Hook Claude Code: /Users/me/.claude/settings.json
  ✅ наша запись hook на месте

Hook Cursor: /Users/me/.cursor/hooks.json
  ✖ нашей записи hook нет

Гейт на запуск (shim в PATH): /Users/me/.geo-guard/bin
  ✅ claude идёт через geo-guard, с твоими флагами: --dangerously-skip-permissions
  ✅ cursor-agent идёт через geo-guard

Запись в PATH: /Users/me/.zshrc
  ✅ /Users/me/.geo-guard/bin добавлен в PATH
  ✅ и ещё в: /Users/me/.bashrc

Страна:
  ✅ RU — разрешена (разрешены: RU, NL)

✖ Чего-то не хватает или что-то сломано (см. строки с ✖ выше).
   Починить: geo-guard setup
```

Код возврата: `0` — всё, что ставит geo-guard, на месте, `1` — чего-то не хватает или что-то сломано, поэтому команду можно использовать в скрипте:

```bash
geo-guard status >/dev/null || geo-guard setup --yes
```

`setup` намеренно не трогает то, что ты правил руками, поэтому цикл сходится на всём, что тот умеет чинить, и останавливается на том, чего не умеет: блок с твоим содержимым внутри маркеров так и будет в отчёте, пока ты сам им не займёшься.

Что проверяется:

- файл конфига: есть ли он и какая политика действует (тот же вывод, что у `geo-guard config`);
- оба hook-файла: есть ли там наша запись **и** пригоден ли файл для установки вообще. Машина без Cursor — это не сломанная установка: `setup` этот хук пропускает, поэтому `status` пишет, что инструмента здесь нет, и не учитывает секцию в коде возврата — битый JSON в `settings.json` или строка вместо объекта в `hooks` попадут в отчёт строкой, а не упадут с ошибкой;
- **каждый гейт по отдельности** (про `cursor-agent` пишется «shim не нужен», если такой команды здесь нет): есть ли наш shim, **с какими флагами он запускает команду** (печатаются, чтобы их было видно, а не приходилось лезть в файл), или на его месте лежит не наш файл (это уже не нормально);
- **действует ли гейт на самом деле**, а не просто установлен. `status` проверяет, что каталог с shim есть в `PATH` того процесса, в котором он запущен, и что shim идёт *раньше* настоящего бинаря. Именно это ловит «setup отработал, но этот shell стартовал раньше», о чём никакой осмотр файлов не скажет. Плюс проверяется, что настоящий бинарь за shim по-прежнему находится: гейт, за которым ничего нет, ломал бы каждый запуск;
- запись в `PATH`: в каком rc она лежит для твоего shell и в каких ещё есть. На Windows дополнительно показывается пользовательский `PATH` (`HKCU\Environment`) — то, что получает каждый новый процесс, включая cmd.exe и всё запущенное из Проводника, — отдельно от `PATH` того процесса, в котором крутится сам `status`;
- **alias-блоки, оставшиеся от прошлой версии**: сообщаются, чтобы мёртвый слой не висел — наши `setup` уберёт, а про чужой скажет, что резать его нам нельзя;
- текущая страна и разрешена ли она. Единственная часть, которая **не** влияет на код возврата: заблокированная страна — это работа `geo-guard check`, а не признак сломанной установки. Без сети пишет `определить не удалось` вместо ошибки.

## Проверка

```bash
geo-guard check; echo $?                          # 0 — ок
GEO_GUARD_ALLOWED=XX geo-guard check; echo $?     # 2 — блок (ты не в XX)
geo-guard check | cat                             # то, что видит хост hook на успехе: {"continue":true}
geo-guard claude --version                        # обёртка запускает claude

```

## Разработка

```bash
npm install          # husky + build (prepare)
npm run typecheck
npm run build
npm test
npm run test:e2e      # настоящий CLI против песочного $HOME, только POSIX
npm run test:pack     # npm pack → установка тарбола → смоук-тест
```

`npm test` гоняет `test/*.test.cjs` — они разложены по областям (`config`, `alias`, `shim`, `shell-path`, `hooks`, `check`, `setup`, `status`, `core`), плюс `hook-invariants`: он на паре десятков форм `settings.json` и `hooks.json` проверяет, что мы никогда не удаляем чужую запись и никогда не переписываем файл, из которого ничего не вынули.

`scripts/windows-smoke.ps1` закрывает то, что двум `sh`-скриптам выше недоступно: powershell-ветку записи в `PATH`, `.cmd`-форму shim, `%APPDATA%` для конфига, разрешение через `PATHEXT` и запуск `.cmd`, чтение hook-payload из stdin и `status`. Ему нужен Windows, поэтому его гоняет CI — см. ниже.

`npm run test:docker` гоняет набор на настоящих дистрибутивах Linux с машины, которая Linux не является. Какой файл читает login-shell bash — свойство дистрибутива, а не нашего кода: Debian кладёт `~/.profile` и такой `~/.bashrc`, который для неинтерактивного шелла делает `return` раньше, чем дойдёт до дописанного нами; Fedora кладёт `~/.bash_profile`; Alpine не кладёт ничего, и bash там нет вовсе. Мок `$HOME` в юнит-тестах проверяет наши представления об этом, контейнер — сам факт. Нужен запущенный Docker (или OrbStack); на каждом дистрибутиве прогоняются юнит-тесты, `test:e2e` и проверка, что запись в `PATH` легла в тот файл, который bash этого дистрибутива действительно читает, — и что `uninstall` возвращает все файлы байт-в-байт.

Git hooks (Husky):

- **pre-commit** — `npm run typecheck`
- **pre-push** — `npm run typecheck && npm test && npm run test:e2e && npm run test:pack`

CI прогоняет полный набор на Ubuntu для Node 18.20 / 20 / 22, на macOS (там своя ветка: login-shell bash читает `~/.bash_profile`, а не `~/.bashrc`) и на Windows — для нижней границы `engines` и текущего релиза. Ось версий Node живёт на Ubuntu; две другие ОС стоят ради платформ, а не ради версий. Windows-job гоняет юнит-сюиту и `windows-smoke.ps1`; `test:e2e` и `test:pack` там не запускаются — они сами себя скипают на Windows, а зелёная галка со смыслом «ничего не проверено» хуже отсутствия job вовсе. Свою полезность этот job окупил на первом же запуске: поймал, что `spawn` отказывается запускать `.cmd` без шелла (CVE-2024-27980, ровно в тех версиях Node, которые названы в `engines`) — то есть `geo-guard claude` на Windows не запускал Claude Code в принципе, ведь npm ставит глобальные CLI именно как `.cmd`-шимы.

### Ручной чек-лист перед релизом

`test:e2e` работает в песочном `$HOME`, поэтому не видит, как *настоящие* Cursor / Claude Code читают *настоящие* конфиги. Перед релизом, на машине с обоими установленными:

1. `geo-guard setup --cursor` → заблокировать промпт в чате Cursor из запрещённой страны → убедиться, что блокирует нашим текстом, и что в логе hooks видна строка `Removed duplicate claude-user hook for beforeSubmitPrompt: command:geo-guard check` (панель Output → канал hooks) — признак того, что проверка ушла один раз, а не дважды.
2. Выключить в Cursor настройку **Third-Party Imports** → блокировка выше должна продолжать работать, теперь чисто через `~/.cursor/hooks.json`.
3. `geo-guard check | cat` → байт в байт `{"continue":true}`, без завершающего перевода строки и лишнего вывода.
4. С **разными странами по инструментам** (`geo-guard config --countries <разрешённая> --profile claude` и `--countries <запрещённая> --profile cursor`): промпт в Claude Code проходит, промпт в Cursor блокируется; поменять списки местами и убедиться, что поведение зеркалится. Это единственная проверка того, что определение хоста в рантайме работает против настоящих хостов — профиль читается из payload, который каждый из них пишет в stdin, а `test:e2e` этих payload не видит вовсе. Заодно убедиться, что строка `Removed duplicate claude-user hook` в логе hooks Cursor всё ещё на месте: если она пропала, два конфига разъехались и Cursor гоняет проверку дважды на каждый промпт.

5. В **новом терминале** `command -v claude` должен указывать в `~/.geo-guard/bin`, а `geo-guard status` — завершаться с кодом 0. Это единственная проверка того, что запись в `PATH` попала в файл, который шелл действительно читает: `test:e2e` не видит, какие файлы сорсит твой терминал, а `npm run test:docker` отвечает только за дистрибутивы из своей матрицы.
